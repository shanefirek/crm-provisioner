## P10 — Host concurrency + retry correctness (audit findings #2-6)

Five fixes, one logical theme: the apply boundary is not concurrent-safe and the retry policy doesn't honor what the principle doc requires.

- **Deliverables:**
  1. Shallow-clone `cached.plan` before mutation/dispatch in `src/host/mcp.ts` (apply tool) — `unblockSteps` currently aliases the cache entry; two concurrent applies on the same `plan_id` corrupt each other's step index.
  2. Pass `client` (not the module-level pool) to `recordPermanentFailure` — cache writes currently bypass the open transaction; a commit failure leaves phantom blocks.
  3. Sequential `await` on the step-write callback's `client.query` calls — `node-postgres` `PoolClient` is not safe for concurrent dispatch.
  4. Drop the 10s `capMs` on `Retry-After` for `kind: "rate_limit"` in `src/host/errors.ts` `computeDelay` — a vendor `Retry-After: 60` is currently silently capped, burning attempts.
  5. Require `api_domain` on Zoho `ConnectionContext`; `mintAccessToken` throws `ConfigError` if absent — fixes silent fall-back to `zohoapis.com` that breaks every non-`com` DC customer (configuration-philosophy tier-2 fail-at-boot).
- **Gate:** existing 66/66 holds. Two new smoke assertions: (a) concurrent applies on the same plan_id produce isolated results (clone correctness, asserted via stepped fixtures in memory adapter); (b) standalone Node script asserts `computeDelay({kind:"rate_limit"}, attempt:0, retryAfterSec:30) === 30000` and `=== 60000` for 60. One ConfigError negative test: Zoho connect without `api_domain` → `ConfigError`, no fall-back.
- **Defer:** per-step PoolClient checkout from the pool (the sequential-await fix is sufficient for v1 throughput); circuit breakers (still deferred per the error-handling defer column "until an outage we needed one for"); cross-connection plan_id collision (each connection has its own cache keyspace).
- **Principles honored:** error-handling-philosophy (Retry-After honored per the retry decision matrix); multi-tenancy-isolation (concurrent isolation between in-flight applies); configuration-philosophy (Zoho api_domain is tier-2 tenant config, fail-at-boot not fall-back).

## P14 — Token at-rest encryption (configuration-philosophy + multi-tenancy blast-radius)

`connections.refresh_token` is stored plaintext. Acceptable for a one-builder demo against Shane's dev orgs; unacceptable the moment a real customer's tokens go in. The pgcrypto path is the standard Postgres pattern; the encryption key is tier-1 env-var (per-environment, per-deployment); the encrypted ciphertext is tier-2 tenant data. This phase aligns the storage with the principle.

- **Deliverables:**
  1. Migration 0006: enable `pgcrypto` extension; rename `refresh_token` → `refresh_token_encrypted bytea`; same for `access_token` → `access_token_encrypted bytea`. Existing rows get re-encrypted in-place via the migration (one-shot — there are only test connections at this point).
  2. New env var `TOKEN_AT_REST_KEY` (32-byte secret, base64-encoded in `.dev.vars`). Server boot validates presence + non-empty; refuses to start if missing (configuration-philosophy tier-2 fail-at-boot).
  3. `loadConn` decrypts via `pgp_sym_decrypt(refresh_token_encrypted, $key)` returning the plaintext token to the adapter (in-memory only, never logged).
  4. `connect_crm` encrypts incoming `refresh_token` + `access_token` via `pgp_sym_encrypt(...)` on insert.
  5. Document KMS-wrapping as P-future in `docs/decision-log.md` — env-var key is acceptable for Railway-on-managed-infra; production with a real customer should wrap the key with Railway's secret manager or external KMS (AWS KMS / GCP KMS).
- **Gate:**
  - Default smoke 79/79 holds (memory adapter never touches tokens).
  - `ZOHO_LIVE=1`: clean connection round-trip — create connection, restart server (so the in-memory access_token cache is cold), inspect_instance → success (server can decrypt + mint). 18 ZOHO_LIVE assertions hold.
  - DB inspection: `SELECT octet_length(refresh_token_encrypted), encode(refresh_token_encrypted, 'hex') FROM connections LIMIT 1` returns ciphertext (binary, length > original) — not the plaintext refresh token. Hand-verifiable.
  - Missing `TOKEN_AT_REST_KEY` → server exits 1 at boot with an instructive error (not silently degrades to plaintext).
- **Defer:**
  - Key rotation (one key for v1; rotation pattern is a P-future entry in decision-log with the canonical 2-key-overlap approach).
  - HSM / KMS integration (env-var key with Railway secret manager is enough for v1; KMS swap is one function-replacement when the customer asks).
  - Per-tenant encryption keys (one global key for v1; per-tenant keys are over-engineered before a multi-customer signal).
  - Audit log of decrypt-access events (logging is the next-principle-doc gap; out of scope here).
  - Encryption of any other connection field beyond tokens (org_label, api_domain, etc. are not secrets; leave plaintext).
- **Principles honored:** configuration-philosophy (tier-1 env-var holds the key, tier-2 tenant column holds the ciphertext, fail-at-boot on missing config); multi-tenancy-isolation (per-tenant blast-radius bounded — token leak from one tenant doesn't compromise the others because each is encrypted with the same key but separately decrypted at use-time; full per-tenant key is the deferred next-step).
