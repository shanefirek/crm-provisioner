## P10 — Host concurrency + retry correctness (audit findings #2-6)

Five fixes, one logical theme: the apply boundary is not concurrent-safe and the retry policy doesn't honor what the principle doc requires.

- **Deliverables:**
  1. Shallow-clone `cached.plan` before mutation/dispatch in `src/host/mcp.ts` (apply tool) — `unblockSteps` currently aliases the cache entry; two concurrent applies on the same `plan_id` corrupt each other's step index.
  2. Pass `client` (not the module-level pool) to `recordPermanentFailure` — cache writes currently bypass the open transaction; a commit failure leaves phantom blocks.
  3. Sequential `await` on the step-write callback's `client.query` calls — `node-postgres` `PoolClient` is not safe for concurrent dispatch.
  4. Drop the 10s `capMs` on `Retry-After` for `kind: "rate_limit"` in `src/host/errors.ts` `computeDelay` — a vendor `Retry-After: 60` is currently silently capped, burning attempts.

One ConfigError negative test: Zoho connect without `api_domain` → `ConfigError`, no fall-back.
- **Defer:** per-step PoolClient checkout from the pool (the sequential-await fix is sufficient for v1 throughput); circuit breakers (still deferred per the error-handling defer column "until an outage we needed one for"); cross-connection plan_id collision (each connection has its own cache keyspace).
- **Principles honored:** error-handling-philosophy (Retry-After honored per the retry decision matrix); multi-tenancy-isolation (concurrent isolation between in-flight applies); configuration-philosophy (Zoho api_domain is tier-2 tenant config, fail-at-boot not fall-back).

## P14 — Token at-rest encryption (configuration-philosophy + multi-tenancy blast-radius)

`connections.refresh_token` is stored plaintext. Acceptable for a one-builder demo against Shane's dev orgs; unacceptable the moment a real customer's tokens go in. The pgcrypto path is the standard Postgres pattern; the encryption key is tier-1 env-var (per-environment, per-deployment); the encrypted ciphertext is tier-2 tenant data. This phase aligns the storage with the principle.

- **Deliverables:**
  1. Migration 0006: enable `pgcrypto` extension; rename `refresh_token` → `refresh_token_encrypted bytea`; same for `access_token` → `access_token_encrypted bytea`. Existing rows get re-encrypted in-place via the migration (one-shot — there are only test connections at this point).
  2. New env var `TOKEN_AT_REST_KEY` (32-byte secret, base64-encoded in `.dev.vars`). Server boot validates presence + non-empty; refuses to start if missing (configuration-philosophy tier-2 fail-at-boot).
  3. `loadConn` decrypts via `pgp_sym_decrypt(refresh_token_encrypted, $key)` returning the plaintext token to the adapter (in-memory only, never logged).
  4. `connect_crm` encrypts incoming `refresh_token` + `access_token` via `pgp_sym_encrypt(...)` on insert.
  5. Document KMS-wrapping as P-future in `docs/decision-log.md` — env-var key is acceptable for Railway-on-managed-infra; production with a real customer should wrap the key with Railway's secret manager or external KMS (AWS KMS / GCP KMS).
- **Gate:**
  - Default smoke 79/79 holds (memory adapter never touches tokens).
  - `ZOHO_LIVE=1`: clean connection round-trip — create connection, restart server (so the in-memory access_token cache is cold), inspect_instance → success (server can decrypt + mint). 18 ZOHO_LIVE assertions hold.
  - DB inspection: `SELECT octet_length(refresh_token_encrypted), encode(refresh_token_encrypted, 'hex') FROM connections LIMIT 1` returns ciphertext (binary, length > original) — not the plaintext refresh token. Hand-verifiable.
  - Missing `TOKEN_AT_REST_KEY` → server exits 1 at boot with an instructive error (not silently degrades to plaintext).
- **Defer:**
  - Key rotation (one key for v1; rotation pattern is a P-future entry in decision-log with the canonical 2-key-overlap approach).
  - HSM / KMS integration (env-var key with Railway secret manager is enough for v1; KMS swap is one function-replacement when the customer asks).
  - Per-tenant encryption keys (one global key for v1; per-tenant keys are over-engineered before a multi-customer signal).
  - Audit log of decrypt-access events (logging is the next-principle-doc gap; out of scope here).
  - Encryption of any other connection field beyond tokens (org_label, api_domain, etc. are not secrets; leave plaintext).
- **Principles honored:** configuration-philosophy (tier-1 env-var holds the key, tier-2 tenant column holds the ciphertext, fail-at-boot on missing config); multi-tenancy-isolation (per-tenant blast-radius bounded — token leak from one tenant doesn't compromise the others because each is encrypted with the same key but separately decrypted at use-time; full per-tenant key is the deferred next-step).

## P15 — Fix the 4 customer-burning bugs from the high-effort review

Four CONFIRMED Tier-1 findings from the 2026-06-13 code-review pass; each is small, scoped, and a direct customer-readiness gate. Bundled because they share a theme (silent-write-loss / parallel-evolution drift at the adapter↔host boundary) and each is ≤30 min on its own.

- **Deliverables:**
  1. **PermissionSet FLS race — `pg_advisory_xact_lock` at the host apply boundary** (`src/host/mcp.ts` apply tool). Lock key: `hashtext('apply-' || conn.crm || '-' || coalesce(conn.api_domain, conn.id))`. Acquired inside the open transaction; auto-released on commit/rollback. Forces concurrent applies against the same SFDC org (or Zoho org) to serialize through the read-modify-write window. Applies uniformly across all CRMs — host-level concern, not adapter-specific.

## P20 — Adopt-or-create on field operations (first general-capability phase since the MVP)

The first new *product capability* since P9; everything since was hardening. Prior-art `prior-art-public-app-provisioner.md` #2/#6 named this as the #1 customer-#1 blocker: when a real org already has a field by the target name, we must attach to it, not collide or silently mis-adopt. Today both adapters emit `diff:"noop"` on an exact-name match (`salesforce.ts:180`, `zoho.ts:181`) — which is *silent adoption with no shape check*: a customer field named `property_address` typed as number would noop against our text spec and we'd report success. This phase makes adoption explicit, shape-checked, and teardown-safe. **One real thing: adopt-or-create on fields.** The per-customer name override that makes adoption fire when the customer's field name differs from ours is the explicit next phase (P21), not this one.

- **Deliverables:**
  1. **New `diff` state `"adopt"`** (`src/adapters/types.ts:23` enum). Distinct from `noop` and `create` so the human confirming the plan (ai-output-handling tier-4) SEES "attaching to your existing field X" before `apply` writes. Lifecycle scaffold (`src/adapters/lifecycle.ts`) treats `adopt` like `noop` for write-skipping but records provenance (below).
  2. **Snapshot shape enrichment.** Both adapters' field snapshot rows currently carry only `{id, api_name}`. Add the shape needed for compatibility: SFDC Tooling query gains data-type (+ length where applicable); Zoho `/settings/fields` already returns `data_type`/`length` — capture them. Memory adapter snapshot mirrors the shape so the default smoke can exercise both branches.
  3. **Shape-compatibility check in `plan()` (both adapters).** On exact-name match: compatible shape (type matches; length ≥ spec) → `diff:"adopt"`. Incompatible (type mismatch, or length too small) → **instructive reject** (error-handling data-error): `plan` returns a DataError-shaped rejection naming the field, the actual shape, and the expected shape, so the agent re-authors — never silent `noop`, never auto-mutate.
  4. **Provenance in the run ledger.** Each adopt/create step records `provenance: "created" | "adopted"` in `run_steps.result_json` (no migration — column is already JSON).
  5. **Teardown safety (the non-negotiable).** `teardown_run` in both adapters reverses only steps with `provenance:"created"`; steps with `provenance:"adopted"` are skipped with an explicit `skipped_adopted_not_owned` note. We never DELETE a field we merely adopted.
  6. **`adopt_if_exists` spec property** on field entities, schema-validated through the overlay resolver's default-deny, defaulting `true` for fields. (Stages/pipelines keep create-only this phase.)
- **Gate (verifiable):**
  - **Default smoke** (memory adapter, no live CRM): seed a field out-of-band → `plan` emits `diff:"adopt"` (asserted, not `create`/`noop`) → `apply` writes `provenance:"adopted"` to `run_steps.result_json` (SQL-asserted) → `teardown_run` leaves the field present (asserted) with a `skipped_adopted_not_owned` step. Plus a shape-mismatch seed → `plan` returns the instructive DataError naming actual-vs-expected. Target: default 89 → ~95.
  - **`SF_LIVE=1`**: out-of-band-create a custom field in `shane-dev` with a spec field's api_name and (a) matching shape → `plan` adopt, `teardown_run`, then Tooling query proves the field STILL EXISTS; (b) mismatched type → `plan` rejects with the instructive error.
  - **`ZOHO_LIVE=1`**: same two cases against the trial via `/settings/fields`.
- **Defer:**
  - **P21 — tenant-level per-customer target-name override** (stable-key rename: "use `referral_source` instead of `lead_source`"). This is what makes adopt fire for the common case where the customer's field name ≠ ours; it's tier-2 tenant config on the delta/connection (configuration-philosophy), a genuinely separable schema+resolver concern. Adopt-by-exact-name (P20) is real and gate-able on its own (re-apply idempotency + customers who use our names) and sets up P21 cleanly.
  - Adopt on **stages/pipelines** (default off; the Zoho whole-array stage replace makes adopting an existing pipeline a clobber risk — needs its own design).
  - **Modifying** an adopted field (label/options PATCH) — that's reconcile (prior-art #6), a later phase. P20 adopts as-is, never mutates.
  - Adopting **standard** (non-custom) fields with any modify path.
  - Affected-assets / blast-radius reporting (prior-art #3) — separate phase.
- **Principles honored:** error-handling-philosophy (shape mismatch is a *data error* → instructive reject, not silent noop, not auto-mutate); ai-output-handling tier-4 (`diff:"adopt"` surfaces the material fact to the human before the write is confirmed); multi-tenancy-isolation + destructive-op safety (provenance guarantees `teardown_run` never deletes a customer-owned field — the scariest blast-radius closed); configuration-philosophy (P20's `adopt_if_exists` default is tier-3 artifact behavior; the deferred P21 name-override is tier-2 tenant config — flagged now so it lands in the right tier); build-iteration-discipline (one real thing — adopt-or-create on fields; name-override deferred to keep the phase bounded).
